# API の展望(今回はやらないこと)

API 設計(issue #15)のゲートで「やりたいが、今回はやらない」と決めたことを残す。
やるときは、ここから台帳(`review-ledger.yaml`)と概念設計に戻して設計する。

| # | やりたいこと | 今回やらない理由・いまの形 | 決めた日・台帳 | やるときに変わるもの |
|---|---|---|---|---|
| 1 | 出展者のアカウント。出展者が自分の企画(時間・説明など)を直せる | 今回は運営だけが呼べる(Cloudflare Access で守る)。出展者の変更は運営に頼む | 2026-11-22・API-12 | 場所に持ち主の項目が要る(概念設計の変更)。「自分の場所だけ直せる」認可と、その 403 のエラー。OQ-1 |
| 2 | ロール分けが要る実体のデータ(出展者の在庫状況など)を扱い、リアルタイムで反映する | 今回はこの種類のデータを扱わない。#1 の出展者のアカウントが前提になる | 2026-11-22・API-12 の回答のとき | 在庫などを持つ新しい概念。出展者だけが更新できる認可。変更を画面に届ける口(API-24 で決める仕組みを使い回す) |
| 3 | 運営が企画を営業停止にしたとき、一覧に残して「停止中」と出し、再開もできる | 今回は場所の削除で表す。再開するときは登録し直す(id が変わり、来場者のタグも外れる) | 2026-11-22・API-26 | Place に「営業中・停止中」の状態と、停止・再開のアクション(概念設計の変更)。流す出来事が placeRemoved から placeUpdated などに変わる |
| 4 | 入力の誤りを、すべての項目についてまとめて返す(運営の登録画面で、誤りを一度に全部出す) | 今回は、誤っている項目を 1 つだけ field で返す | 2026-11-22・API-15 | エラーの形に、誤りの一覧(errors: [{field, message}])を足す |

ロール分けが要らない共有のデータ(スタンプなど)のリアルタイム反映は、**今回やる**(台帳 API-24)。
