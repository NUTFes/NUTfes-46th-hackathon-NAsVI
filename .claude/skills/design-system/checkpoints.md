# 人間が確かめるべき点(AI に任せるとき)

出どころ: 別セッションでの整理案(仮説)。特定の書籍の主張ではない。運用しながら調整する。

## 確認の基準

次のどれかに当てはまる判断は、AI の案でも人間が確認する。

1. **実体験・現場の情報に依存するもの**: 実際に使ったときの迷い、引っかかり。AI は持っていない。
2. **やり直しが高くつくもの**: 公開した API 契約、データモデル、命名と分類の方針。
3. **価値判断・優先順位**: 何を作るか、作らないか、原則のどれを優先するか。
4. **AI が自分で検証できないもの**: もっともらしい理由づけは、正しさの証拠にならない。
5. **層をまたぐ整合**: 概念、API、画面、部品がお互いに矛盾していないか。

## デザインシステムの段階での分担

| | AI に任せてよい | 人間が確認する | 確認の方法 |
|---|---|---|---|
| トークン・コンポーネント | トークンの下書き(DTCG 形式など)、コンポーネント仕様書、命名案 | 命名と分類の方針、原則の優先順位、例外の扱い | 既存の画面で適用してみて矛盾が出ないか。アクセシビリティは自動検査と実機確認を併用 |
| 実装 | コードの下書き、テストの生成 | 設計意図との一致、境界を越えた依存、エラー時の挙動 | 契約テスト、レビュー、実際の画面での動作確認 |

(API 設計・画面設計の分担は、それぞれの skill とドキュメントを見る。)

## 確認の優先順位(やり直しコストの高い順)

1. 概念の境界とデータモデル
2. 公開前の API 契約
3. 課題の定義と、作らないことの決定
4. デザインシステムの命名・分類の方針
5. 画面の詳細、文言、見た目の調整

上にあるものほど、AI の案をそのまま採用せず、根拠まで確認する。

## 確認を実効性のあるものにするコツ

- 案だけでなく、**根拠、代替案、却下した理由、前提**も出させる。
- 「合っているか」ではなく、**反証を探す問い**で確認する。
- 確認を**テストできる形**に落とす(スキーマ検証、コントラスト比の自動検査など。分かるのはアクセシビリティの一部)。
- 人間が確認した事実と、AI が推定した内容を、**文書上で区別する**。

## 未解決(運用で見直す)

- 確認の負荷と、決定の速度のバランス。確認が過剰な箇所と不足している箇所を見直す。
- 実体験のデータ(観察記録)を、どの形式で残して AI に渡すか。
