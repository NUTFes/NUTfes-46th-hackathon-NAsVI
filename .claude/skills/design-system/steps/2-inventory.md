# ステップ 2: 部品を洗い出して分類する

## なぜやるか
画面ごとに同じような部品を別々に作ると、見た目も振る舞いも揃わない。先に「どんな部品が要るか」を全画面から集め、似たものを 1 つにまとめる。

## できあがるもの
- `design-system/inventory.md`: 部品の一覧(名前、役割、どの画面で使うか、見せる概念・項目)。
- 分類と命名の方針(1 ページ)。

## 目安: 45〜90 分

## 前提
`screens.yaml` と、画面ごとの「見せるもの・操作」(`screen-design` のステップ 5)。未完なら、いまある画面の操作から案を作り、`status: proposed` と書く。

## やること
0. **既存のモック・実装があれば、先に棚卸しする**(SKILL.md の「先に既存の成果物を読む」)。class 名・id から、繰り返し出る部品を数える。以降の手順は、この結果を出発点にする。
1. 画面ごとに、見せるものと操作を部品の候補に書き出す。AI が下書きを作る(既存のモックがあれば、そこにある部品と対応づける)。
2. 同じ役割のものを束ねる(例: 場所を示す行が、検索結果にも地図の吹き出しにも出る)。束ねた根拠を書く。
3. **分類の方針**を決める。AI が 2〜3 案を出す(例: Atomic Design の階層で切る / 機能的パターンと知覚的パターンで切る / 概念ごとに切る)。各案に、この一覧でどう分かれるかを実際に当てる。
4. **命名の方針**を決める(例: 概念名を頭に付ける `PlaceRow`、役割で付ける `ListRow`)。
5. 各部品が見せる項目を、API のレスポンスの項目と照合する。API 設計が未完なら、「見せたい項目」の一覧を API 側に渡す(台帳に残す)。
6. 決定ログに、分類と命名の方針、却下した案を残す。

## 評価基準(次に進む条件)
- [ ] `screens.yaml` の全画面の「見せるもの・操作」が、いずれかの部品に対応している(漏れなし)
- [ ] 部品ごとに、使う画面が 1 つ以上ある(画面のない部品は作らない)
- [ ] 分類の方針を実際の一覧に当てて、**どちらにも入る部品**と**どこにも入らない部品**を列挙してある
- [ ] 見せる項目の一覧が、API 設計側と共有されている
- [ ] **人間の確認**: 分類・命名の方針(やり直しコストが高い)を、人間が根拠まで見て決めた

## 反証の問い
- この分類で、どちらにも入る部品はあるか。そのとき置き場をどう決めるか。
- 2 つに分けた部品は、本当に別々に変わるか。同じ理由で一緒に変わるなら、1 つにすべきではないか。
- 名前を見て、画面を見ていないメンバーが役割を当てられるか。
