# ステップ 5: 画面に当てて確かめる

## なぜやるか
部品は、単体では良く見えても、実際の画面に並べると矛盾が出る(余白がずれる、同じ役割の部品が 2 つある、データが長いと崩れる)。当てて確かめてから実装に渡す。

## できあがるもの
- `design-system/apply-log.md`: 画面ごとに当てた結果と、見つかった矛盾、直した内容。
- 「実装に渡せる」かどうかの判定([SKILL.md](../SKILL.md) の完了条件)。

## 目安: 60 分

## やること
1. 画面設計(#16 の画面、または `screens.yaml`)の画面を、部品とトークンだけで組み直す(Figma 上で)。主要なジャーニー F1〜F3 の画面から。
2. 実際のデータの形で当てる。ここでいう「端の場合」は、**うまくいかないときと、極端なデータのときの画面**のこと。
   - #16 にあるもの: V1-c 検索の一致がない、V1-g 位置が使えない、V3-b 建物は分かったが企画がない、V3-c 建物を認識できない。
   - 足して確かめるもの(#16 にはない): 企画名がとても長い、絞り込みの結果が 0 件、お気に入りが 0 件、同じ場所にスタンプが多数重なる、読み込み中と通信エラー。
3. 矛盾を記録する。AI が列挙し、人間が重要度を判断する。
   - 部品が足りない → ステップ 2 に戻る
   - 部品の props が足りない → ステップ 4
   - トークンが足りない → ステップ 3
4. アクセシビリティを、自動検査(コントラストなど)と実機確認で確かめる。AI は検査の手順を出し、**実機での確認は人間が行う**。
5. 完了条件をすべて見て、満たしていない項目を一覧にする。満たしていなければ、どのステップに戻るかを書く。
6. 決定ログの「未確認」の決定を一覧にして、実装者に伝わる場所に置く。

## 評価基準(次に進む条件)
- [ ] 主要ジャーニーの全画面が、部品とトークンだけで組めている(画面だけの特別な部品がない)
- [ ] うまくいかないとき・極端なデータのとき(上の 2.)を、各画面で 1 つ以上当てた
- [ ] 矛盾の記録があり、すべて「直した / 後で / 直さない(理由)」のどれか
- [ ] 実機で、明るい場所・片手操作で見て確かめた記録がある
- [ ] SKILL.md の完了条件がすべて満たされている

## 反証の問い

- データが 2 倍長いと、どこが崩れるか。
- 色を見分けられない人には、混雑の状態が伝わるか。
