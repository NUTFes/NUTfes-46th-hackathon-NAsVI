# ステップ 3: トークンを決める

## なぜやるか
色・余白・文字の大きさなどを、値そのものでなく「名前つきの値(トークン)」で持つと、見た目の変更が 1 か所で済み、Figma とコードで同じ値を使える。

## できあがるもの
- `design-system/tokens.json`: DTCG 形式のトークン([templates/tokens.dtcg.json](../templates/tokens.dtcg.json) が書式の例)。
- Figma の変数(Variables)。`tokens.json` と同じ名前・同じ値。
- 命名の方針(ステップ 2 の命名とは別。トークンの名前の付け方)。

## 目安: 45〜60 分

## やること
0. **既存のモックに CSS 変数(`--bg`, `--violet` など)があれば、そこから起こす**。AI が変数を一覧にし、「意味のトークン」への割り当て案(例: `--yel` → `color.action.primary`)を出す。直書きの値(角丸 14px、文字 12/13/15/18px など)も数えて、トークンにする候補にする。採否は人間が決める。
1. 原則(ステップ 1)から、知覚的パターン(色、タイポグラフィ、余白、角丸、影、動き)の方向を決める。AI が案を出し、人間が選ぶ。(既存の見た目がある場合は、それが原則に合うかを確かめる。)
2. **トークンの階層**を決める(例: 値そのもの `color.blue.500` → 意味 `color.action.primary` → 部品 `button.background`)。階層を増やしすぎない。AI が 2 案を出し、却下理由も書く。
3. 命名の方針を決める。仕様は命名を直接は制約しないので、チームで決める(Curtis の記事が参考。[reference.md](../reference.md))。
4. AI が `tokens.json` を下書きする。まず必要最小限(使う画面に出る分だけ)。
5. 機械で確かめる: 参照切れ(別トークンへの参照が存在するか)、名前の重複、コントラスト比(文字と背景の組。WCAG の基準で)。
6. Figma の変数に反映する。書き込む前に、何を作るかを人間に伝える。
7. 決定ログに、階層と命名の方針、色の選び方の理由を残す。

## 評価基準(次に進む条件)
- [ ] JSON として読める。参照切れ 0、名前の重複 0(機械で確認)
- [ ] 文字と背景の組のコントラスト比を計算してあり、基準に届かない組は一覧に残している
- [ ] Figma の変数と `tokens.json` が同じ(名前と値)
- [ ] 値の書式を、DTCG 仕様 2025.10 で確かめた(未確認なら「未確認」と書く)
- [ ] **人間の確認**: 階層と命名の方針、色の方向を人間が決めた。屋外・明るい場所で実機で見て確かめた(コントラストの自動検査は一部にとどまる)

## 反証の問い
- 新しい種類の部品を足したとき、この命名で置き場に困らないか。
- ライト/ダークなど文脈が増えたとき、階層のどこで切り替えるか。
- 値そのもののトークンを、部品が直接参照している所はないか。
