# ステップ 4: コンポーネントを仕様にする

## なぜやるか
実装者が「定義を読んでコードにするだけ」にするには、部品ごとに、構造・props・状態・使い方が、迷わず読める形で書かれている必要がある。Figma とコードで、構造(anatomy)と props の名前を揃える。

## できあがるもの
- `design-system/components/<部品名>.md`: 部品ごとの仕様([templates/component-spec.md](../templates/component-spec.md))。
- Figma のコンポーネント(バリアント、props を仕様と同じ名前で)。

## 目安: 部品 1 つにつき 15〜30 分(主要な部品から)

## やること
0. 画面設計の各画面にある「要求」の欄(`Request.*`)を、API 設計の Step 1 の表(画面/機能 × 操作)と直接つなぐ。タグ・絞り込みの要求は端末内で完結するので、API の表には載せない(D-014)。
1. ステップ 2 の一覧から、**使う画面が多い順**に着手する(全部を一度に作らない)。
2. AI が仕様書を下書きする。含めるもの:
   - 目的(1 文)と、使う画面
   - 構造(anatomy): 何の部分でできているか
   - props: 名前、型、必須か、既定値、取りうる値
   - 状態: 通常、押下、無効、読み込み中、空、エラー(必要なものだけ)
   - 使う / 使わない場面
   - アクセシビリティ: 操作方法、読み上げ、押せる大きさ、色だけに頼らない
   - 使うトークン
3. **props ↔ API の照合**(合流点): 部品が受け取る項目が、API のレスポンスにあるか。名前、型、欠けた場合の挙動を並べる。食い違いは「要確認台帳」に書き、API 側のイシューにする。
4. Figma にコンポーネントを作る。構造と props の名前は、仕様書と同じにする。作る前に何を作るかを人間に伝える。
5. 機械で確かめる: 仕様の props の名前が、Figma のバリアント/プロパティの名前と一致しているか。使うトークンが `tokens.json` に存在するか。
6. 決定ログに、props の粒度、例外の扱いを残す。

## 評価基準(次に進む条件)
- [ ] 部品ごとに、仕様書の全項目が埋まっている(空欄は理由つき)
- [ ] 使うトークンが `tokens.json` に全部ある(機械で確認)
- [ ] props の名前が、Figma と仕様書で一致(機械または目視で確認)
- [ ] props ↔ API の照合が済み、食い違いが台帳にある
- [ ] 空・エラー・読み込み中の状態が、必要な部品で描かれている
- [ ] **人間の確認**: props の粒度と、例外の扱いを人間が決めた

## 反証の問い
- この props を 1 つ増やすと、別の部品の仕様も変わるか。
- API の項目が欠けた(null)とき、この部品はどう見えるか。
- 名前を知らない実装者が、この仕様書だけで作れるか。足りない情報は何か。
