# design-system(デザインシステムの構築)

**ゴール**: Figma 上で、トークン(色・余白など)とコンポーネント(部品)の定義が終わり、実装者が「定義を読んでコードにするだけ」になっている。

この skill は、次の 2 つの資料(別セッションで調べた整理案)をもとにしている。どちらも**仮説・整理案**で、特定の書籍の主張ではない。運用しながら直す。
- 何を人間が確かめるか: [checkpoints.md](checkpoints.md)
- 何を・どの形式で書くか(出典つき): [reference.md](reference.md)

## 前提と並行開発

入力は `concept-design/screens.yaml`(どの画面にどの概念・操作があるか)。**部品の洗い出し(ステップ 2)には、画面ごとの「見せるもの・操作」が要る**。これは `screen-design` のステップ 5 の成果物。

### 先に既存の成果物を読む(ゼロから作らない)

メンバーが、すでに画面を作っていることがある。**最初に、既存のモック・実装・Figma を探して棚卸しする**。見つかったら、ステップ 2・3 は「ゼロから決める」でなく「あるものを抜き出して、採否を人間が決める」になる。
- 探す場所: `ar-guide/mock/`(マップのモック。PR #4・#5、fore0111。`main` に入っているかは `git log` / `gh pr list` で確かめる)、`ar-guide/index.html`(AR 画面)、Figma のファイル(リンクは `doc/README.md` やチームの Notion)。
- 抜き出すもの: CSS 変数(= トークンの元)、繰り返し出る部品(class 名)、画面の状態(空・読み込み中・位置なし など)。
- 既存の見た目は**メンバーの選択**。AI は、勝手に作り直さず、棚卸しの結果と、矛盾・不足を出して、採るか変えるかを人間に聞く。
- 結果は `design-system/audit-<対象>.md` に残す。実例: [templates/audit-example.md](templates/audit-example.md)(マップのモックの棚卸し。AI が読んだだけで、画面に描画して確かめてはいない)。

| ステップ | 画面設計の完了を待つか | API 設計との合流 |
|---|---|---|
| 1 原則と言葉 | 待たない(いま始められる) | 用語を API の名前と揃える |
| 3 トークン | 待たない(ステップ 1 のあと) | なし |
| 2 部品の洗い出し | **ステップ 5 を待つ**(未完なら案として進め、proposed と書く) | 部品が見せる項目を、API のレスポンスの項目と照合 |
| 4 コンポーネント仕様 | ステップ 2 のあと | **props と API のレスポンスの形が合うか**を確かめる(合流点) |
| 5 画面に当てて確かめる | 画面が描けてから | 実データの形で当てる |

つまり、画面設計が終わる前に、ステップ 1 → 3 を進めておける。API 設計と並行するときの合流点は、ステップ 2 と 4 の「部品の props ↔ API の項目」。

## 5 つのステップ

1 ステップは 30〜90 分が目安。各ファイルに「なぜやるか / できあがるもの / 次に進む条件」がある。

| # | ステップ | 成果物(見えるもの) | 手順 |
|---|---|---|---|
| 1 | 原則と言葉をそろえる | 原則(優先順位つき)と用語集 | [steps/1-principles.md](steps/1-principles.md) |
| 2 | 部品を洗い出して分類する | 部品の一覧と、分類・命名の方針 | [steps/2-inventory.md](steps/2-inventory.md) |
| 3 | トークンを決める | `design-system/tokens.json`(DTCG 形式) と Figma の変数 | [steps/3-tokens.md](steps/3-tokens.md) |
| 4 | コンポーネントを仕様にする | 部品ごとの仕様と、Figma のコンポーネント | [steps/4-components.md](steps/4-components.md) |
| 5 | 画面に当てて確かめる | 矛盾の記録と、実装に渡せる状態の判定 | [steps/5-apply.md](steps/5-apply.md) |

作業の置き場は `design-system/`(初回に作る)。決定ログは `design-system/decisions.md`、進み具合は `design-system/progress.yaml`(`step`, `done`)。テンプレートは [templates/](templates/)。

## AI の振る舞い(必ず守る)

1. **始めるとき**に、いまのステップ(n / 5)、目的、成果物、目安の時間を先に言う。
2. **任せる範囲を守る**。AI は選択肢の列挙、下書き(トークン、仕様書、命名案)、機械的な整合チェックをする。**命名と分類の方針、原則の優先順位、例外の扱い、公開後に変えにくい部分は、人間が決める**。AI は案と根拠を出して止まる。
3. 案には必ず**根拠・検討した代替案・却下した理由・前提**をつける([templates/decision.md](templates/decision.md))。
4. 確認は「合っていますか」でなく、**反証を探す問い**で頼む(例: 「この分類で、どちらにも入る部品はないか」)。
5. **人間が確かめた事実と、AI の推定を区別して書く**。確認状態は 確認済 / 一部のみ確認 / 未確認。未確認のまま進めるなら、そう明記する。
6. 質問は 1 度に 1 つ。AI の推奨案を 1 つ添える。初めて出る専門用語(トークン、バリアント、props など)は 1 文で説明する。
7. **確認の優先順位**(やり直しが高くつく順)を守る: 概念と用語 → API 契約との整合 → 命名・分類の方針 → 部品の詳細 → 見た目の調整。上のものほど、根拠まで人間が確かめる。
8. 機械で確かめられるものは、その場で確かめる(トークンの参照切れ、コントラスト比、命名の重複)。ただし、自動検査で分かるアクセシビリティは一部にとどまる。実機・実際の操作での確認を、人間に頼む。
9. 終わりに、ここまでで何ができたか(成果物)を具体的に伝え、`progress.yaml` を更新する。
10. 資料の URL や仕様の書式は、書いてあるとおりに使わない。[reference.md](reference.md) の「未確認」を読み、使う前に確かめる。
11. commit・push・PR は、頼まれたときだけ。Figma への書き込みも、何を作るかを先に伝えてから行う(Figma MCP が使えるとき)。

## 「実装するだけ」の判定(完了条件)

次がすべて満たされたら、実装に渡してよい。
- [ ] 全部品に仕様(目的・構造・props・状態・アクセシビリティ)がある
- [ ] props と API のレスポンスの項目が照合済みで、食い違いが台帳に残っている
- [ ] トークンが Figma の変数と `tokens.json` で一致している
- [ ] 全部品が、少なくとも 1 つの実際の画面に当てて、矛盾がないと確かめてある
- [ ] 決定ログに、確認状態が「未確認」のままの決定があれば、実装者に伝わる場所に書いてある
