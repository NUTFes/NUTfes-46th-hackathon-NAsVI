# api-design(OpenAPI 設計。確認ゲートつき)

**ゴール**: `concept-design/api/openapi.yaml` が書けて、人間が決めるべき事項がすべて台帳(`api/review-ledger.yaml`)で「確定」になっており、機械検査が通っている。

この skill は、別セッションで作ったたたき台(確認ゲートつきの OpenAPI 設計スキル)を、このプロジェクトの流れに合わせたもの。**AI が推測で決めてはいけない事項を明示し、人間が確認するゲートを必ず通す**ことが目的。

## 原則

1. DB スキーマ起点にしない。**ユースケース(画面・機能)→ API 契約 → データモデル**の順で考える。レスポンスは DB の構造と切り離す。
2. 公開した API は変えにくい。迷う点は勝手に埋めず、「要確認」として台帳に残す(確認の優先順位は、概念・データモデルの次に、公開前の API 契約が高い)。
3. **ゲートは飛ばさない**。回答がないまま次の工程に進まない。ユーザーが「全部任せる」と明言したときだけ、仮置きで進めて、台帳に全部残す。
4. 人間が確かめた事実と、AI が推定した内容を区別して書く。

## このプロジェクトでの入力

| 入力 | 場所 | 使い方 |
|---|---|---|
| 概念設計 | `concept-design/concepts.yaml` | `Request.*` で始まる同期が、外から呼ぶ操作の元(要求名)。`then` が実行する概念のアクション、`where` が権限・条件、アクションの `requires` が事前条件(エラーの候補) |
| API の元表 | `python3 tools/derive.py api` → `api/actions.generated.md` | メソッドとパスは機械が付けた**仮の値**。ここから Step 1 の表を作る |
| 画面設計 | `concept-design/screens.yaml`(`screen-design` の成果物) | どの画面でどの操作をするか。**画面にない操作を足さない** |
| 未決事項 | `concept-design/open-questions.yaml` | 認証(OQ-1)など、API に効くものは台帳の `related_oq` に結びつける |
| 部品の props | `design-system/components/*.md`(`design-system` の成果物) | 部品が受け取る項目が、レスポンスにあるか(合流点) |
| 既存の API・DB、想定クライアント | 聞く | なければ「新規設計、自社フロントのみ」を仮置きにして台帳へ |

作業開始時に、足りない入力を一覧にして聞く。

## 並行開発(デザインシステムとの合流点)

| API 側のステップ | デザインシステム側 | 合流で確かめること |
|---|---|---|
| Step 1(操作の抽出) | ステップ 2(部品の洗い出し) | 部品が見せる項目の一覧を受け取り、レスポンスに入れる項目と照合する |
| Step 2〜3(ドラフト・決める事項) | ステップ 4(コンポーネント仕様) | 部品の props の名前・型と、レスポンスの項目が一致するか。欠けた(null)ときの挙動 |
| Step 5(整合) | ステップ 5(画面に当てる) | 実際のデータの形で当てても崩れないか |

食い違いは台帳に書き、どちらを直すかを人間が決める。

## 5 つのステップ(ゲートつき)

| # | ステップ | 成果物 | ゲート |
|---|---|---|---|
| 1 | 操作とリソースを抜き出す | 操作の表(画面/機能・要求名・メソッド・パス案) | **ゲート 1**: リソース名、階層、過不足、命名規則 |
| 2 | OpenAPI のドラフトを作る | `api/openapi.yaml`、台帳の初稿 | なし(ゲート 1 の承認後に作る) |
| 3 | 人間が決める事項を確認する | 台帳の更新(確定・仮置き) | **ゲート 2**: 読み取れなかった項目の質問リスト |
| 4 | 機械で検査する | 検査の結果 | なし(ERROR 0 が条件) |
| 5 | 整合を自己点検し、最終確認する | 点検の記録とチェックリスト | **ゲート 3**: 最終チェックリスト |

各ステップの手順と評価基準は [steps.md](steps.md)。ゲート 2 で聞く項目の一覧と、このプロジェクトでの候補は [gates.md](gates.md)。

## 機械検査(ハーネス)

```
cd concept-design
python3 tools/derive.py api                                   # 元表を作り直す
python3 tools/openapi_check.py api/openapi.yaml \
    --ledger api/review-ledger.yaml --concepts concepts.yaml  # 検査(--external で redocly / spectral も)
```

検査すること: 構造と `$ref`、operationId の重複、成功とエラーのレスポンス、例、`Request.*` との対応(`x-request` と `x-excluded-requests`)、台帳との整合(`x-needs-review`)、名前の揺れ。**外部の lint は、入っていなければ「未実施」と出る。「検証済み」と報告してよいのは、実際に走って通ったときだけ。**

## 成果物

1. `api/openapi.yaml`: 仕様書本体。操作に `x-request: <要求名>` を付ける。要確認の箇所に `x-needs-review: "API-n: 理由"` を付ける。
2. `api/review-ledger.yaml`: **要確認台帳**。全ゲートの質問と回答。形式はファイル内のコメントを見る。
3. 完了報告は短く、次の 3 点だけ: ① 作ったもの ② 台帳の未確定件数 ③ 人間にまだ確認してほしいこと

## AI の振る舞い

1. 始めるときに、いまのステップ(n / 5)、目的、成果物、ゲートの有無を先に言う。
2. 質問は 1 度に 1 つ(ゲートの質問リストは、区分ごとに 1 つずつ)。選択肢には、AI の推奨案とその理由を 1 つ添える。
3. 初めて出る用語(冪等性、ETag、operationId、`$ref` など)は 1 文で説明する。
4. 仮置きしたものは、その場で台帳に書く。仕様にだけ書いて台帳に残さない、ということをしない。
5. 決めるのはチーム。入力にない業務ルールや認可条件を、もっともらしく補って**確定扱いにしない**。
6. commit・push・PR は、頼まれたときだけ。

## やってはいけないこと

- 入力にない業務ルールや認可条件を、補って確定扱いにする
- ゲートの回答を待たずに次の工程へ進む
- DB のカラム構造をそのままレスポンスにする
- 台帳に残さず仮置きする
- lint を実行していないのに「検証済み」と報告する
- 画面にない操作を、根拠なくエンドポイントとして足す
