# ゲート 2: 人間が決める事項

AI は、次の事項を**自分で決めない**。選択肢と推奨案を示して、人間に決めてもらう。入力から読み取れなかったものを質問リストにし、回答は台帳に残す。

出どころ: 別セッションの OpenAPI 設計スキルの表。「このプロジェクトでの候補」は、`concepts.yaml` と `open-questions.yaml` を読んで挙げた、こちらの推論(案)。

| 区分 | 確認する内容 | このプロジェクトでの候補 |
|---|---|---|
| 認証・認可 | 認証方式、誰がどの API を呼べるか、リソース所有者チェック | 場所・ランドマークの登録系は「運営のみか、出展者も含めるか」(OQ-1)。来場者を識別するか(OQ-12)で、`u`(利用者)の持ち方が変わる |
| バリデーション | 必須/任意、文字数、形式、一意性、業務ルール | 場所の name・kind・location の必須、スタンプの種類(OQ-4)、Point の形(緯度経度) |
| エラー仕様 | ステータスコードの使い分け、エラーボディの形式、エラーコード体系 | 概念アクションの `requires` が、そのままエラーの候補(例: `Position.update` は `u` が allowed に含まれること) |
| 状態遷移 | 状態の一覧と遷移条件 | 位置情報の許可/拒否、行き先の選択/解除、スタンプの押す/取り消す |
| 一覧取得 | ページング方式、上限、ソート・絞り込み項目 | `showPlaces` の絞り込み(Labeling。OQ-3)、`showStamps` の許容時間(OQ-4)、場所の件数の見込み |
| 冪等性・競合 | 再送時の挙動、同時更新の扱い | スタンプの連打、`reportPosition` の再送、場所の同時更新 |
| 個人情報・機密 | レスポンスに含めてよい項目、マスキング、ログ出力 | 現在地は自分のみ(概念の原理)。他人の位置を返さないこと。建物認識の画像は保存・送信しない(OQ-11) |
| 互換性 | バージョニング方針、破壊的変更の定義 | ハッカソンの期間内は版を付けない、という仮置きが現実的(推論) |
| 非機能 | レート制限、タイムアウト、最大リクエストサイズ | 来場者数の見込み(OQ-6)に依存 |
| リソース設計 | 1 回の要求で複数の概念が動くときの失敗の扱い | `actions.generated.md` の 2 章の連動 |
| 命名 | 複数形、ケース、動詞の扱い | Step 1 のゲート 1 で決める |

## 質問の出し方
- 区分ごとに、1 つずつ聞く。
- 選択肢は 2〜3 個、推奨を 1 つ、推奨の理由を 1 文。
- 「合っていますか」でなく、反証を探す問いで聞く(例: 「この認可で、出展者が他の出展者の場所を更新できてしまうケースはあるか」)。
- 回答が「まだ決められない」なら、`OQ-n` として open-questions.yaml に載せるか、台帳に「要確認」で残す。決めずに進めない。
