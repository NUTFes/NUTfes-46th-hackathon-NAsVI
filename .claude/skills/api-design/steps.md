# 各ステップの手順と評価基準

作業場所は `concept-design/`。

## Step 1: 操作とリソースを抜き出す

**なぜやるか**: 画面で人がする操作から、API が提供すべきものを逆算する。DB の都合から作ると、画面に要らない API が増える。

**できあがるもの**: 操作の表。

| 画面/機能 | 要求名(`Request.*`) | 操作 | メソッド | パス案 | 備考 |
|---|---|---|---|---|---|

**やること**
1. `python3 tools/derive.py api` で元表を作り、`Request.*` を 1 行ずつ表に写す。仮のメソッド・パスは「決める」ものとして扱う。
2. `screens.yaml` の画面・操作と突き合わせる。画面にあって要求がない操作、要求があって画面にない操作を列挙する。
3. リソース名と階層、命名規則(複数形、ケース、動詞の扱い)の案を、代替案つきで出す。
4. 1 回の要求で複数の概念が動くもの(`actions.generated.md` の 2 章)は、失敗時に全体を失敗にするか一部成功にするかを、質問として挙げる(台帳へ)。

**評価基準**
- [ ] 全 `Request.*` が、表に載っている(漏れなし)
- [ ] 画面にない操作に、理由がある(または表から外した)
- [ ] 命名規則の案が、代替案とともに示されている

**【ゲート 1: 人間が確認】** リソース名と階層は意図どおりか / 過不足のない一覧か(画面にない操作を足していないか) / 命名規則(複数形、ケース、動詞)。回答がないまま Step 2 に進まない。

## Step 2: OpenAPI のドラフトを作る

**できあがるもの**: `api/openapi.yaml`。台帳の初稿。

**やること**
1. `components/schemas` にスキーマを切り出し、`$ref` で再利用する。レスポンスは画面が要る項目から決める(DB の列から決めない)。
2. 各操作に `operationId`(要求名と同じにするのを推奨)、`summary`、`tags`、成功とエラーのレスポンス、`x-request` を書く。
3. 例(`example`)を最低 1 つ付ける。
4. 確認が必要な箇所に `x-needs-review: "API-n: 理由"` を付け、同じ id の項目を台帳に書く。推測で埋めた項目は、**仮置き**として placeholder に内容を書く。
5. 対応させない要求は、トップレベルの `x-excluded-requests: {要求名: 理由}` に書く(例: 未決の OQ で外したもの)。
6. 部品が見せる項目(デザインシステム側)があれば、レスポンスの項目名・型を合わせる。

**評価基準**
- [ ] `python3 tools/openapi_check.py ...` で、構造・`$ref`・operationId・レスポンス・対応の ERROR が 0
- [ ] 推測で埋めた項目が、すべて台帳にある

## Step 3: 人間が決める事項を確認する(必須)

**なぜやるか**: 認証、バリデーション、エラーの形などは、入力から読み取れず、後で変えにくい。AI が補うと、もっともらしい誤りが入る。

**やること**: [gates.md](gates.md) の区分ごとに、入力から読み取れなかった項目を質問リストにする。各質問に選択肢と推奨案、推奨の理由を付ける。回答を仕様に反映し、台帳を「確定」(決定者・日付つき)に更新し、仕様から `x-needs-review` を外す。

**評価基準**
- [ ] gates.md の全区分に、「入力から読み取れた / 質問した / 該当なし(理由)」のどれかの記録がある
- [ ] 人間が答えたものだけが「確定」になっている(decided_by と date がある)
- [ ] 答えがないものは、「要確認」か「仮置き」のまま台帳に残っている

**【ゲート 2: 人間が確認】** 質問リストへの回答を得る。

## Step 4: 機械で検査する

`python3 tools/openapi_check.py api/openapi.yaml --ledger api/review-ledger.yaml --concepts concepts.yaml --external`

**評価基準**
- [ ] ERROR 0
- [ ] WARN は、理由を言えるものだけが残っている
- [ ] 外部 lint を実行したか、「未実施」かを、報告に明記した
- [ ] x-needs-review の残数を報告した

## Step 5: 整合を自己点検し、最終確認する

**AI の自己点検**
- 画面設計の全項目が、いずれかのレスポンス/リクエストに対応しているか
- 概念設計のアクションが、操作に現れているか(機械検査は要求単位。アクション単位で漏れがないか)
- 同じ概念が別の名前で出ていないか(`userId` と `user_id`。機械検査の名前の揺れを見る)
- 画面にない項目を、根拠なく足していないか
- 部品の props とレスポンスの項目の食い違いが、台帳にあるか

**【ゲート 3: 人間が最終確認】** 次のチェックリストを提示する。
- [ ] 画面の全ケース(一覧、詳細、登録、更新、削除、エラー表示)が API で実現できる
- [ ] 認証・認可の方針が意図どおり
- [ ] 公開してはいけない項目がレスポンスに含まれていない
- [ ] エラー時にクライアントが取るべき動作を判断できる
- [ ] 名前の揺れがない
- [ ] `x-needs-review` が残っていない(残すなら理由が台帳にある)

**完了報告**: ① 作ったもの ② 台帳の未確定件数 ③ 人間にまだ確認してほしいこと(3 点だけ。短く)。
