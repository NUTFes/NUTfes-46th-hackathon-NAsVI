# 台本：API 設計の基礎

## API 設計の基礎 {#s-s34u6k}
[0] この資料は、API の設計が初めての人が、確認ゲートで判断できるようになるためのものです。必要な知識だけを、定義から順に積み上げます。

## API とは約束である {#s-gvyyl6}
[0] まず、API とは何かです。使う側と作る側のあいだに、決まりごとを置きます。
[1] 使う側は、たとえばスマートフォンの画面です。
[2] 真ん中に置く決まりごとが、API です。何を頼めるか、何が返ってくるかの約束です。
[3] 作る側は、データを持っているサーバーです。
[concl] 約束さえ決まれば、画面側とサーバー側は別々に作れます。

## 1 回の通信は要求と応答 {#s-fba6ak}
[0] API を使うと、1 回ごとに、呼ぶ側が要求を送り、作る側が応答を返します。
[1] 要求は、メソッドとパスと中身でできています。メソッドは「何をしたいか」、パスは「どれに対してか」です。
[2] 応答は、ステータスと中身でできています。ステータスは、結果を表す数字です。
[3] たとえば、場所の一覧を頼むと、成功を表す二百と、場所の一覧が返ってきます。
[concl] どんな API も、この往復の組み合わせでできています。

## 「もの」と「すること」を分ける {#s-zaj5yt}
[0] ここが設計の出発点です。HTTP の仕様である RFC 9110 では、要求の対象を「リソース」と呼びます。
[1] 悪い例では、動詞が URL に入っています。取る、消す、押す、のたびに、新しい URL が増えてしまいます。
[2] 良い例では、URL は「もの」だけを指します。「すること」は、メソッドが表します。
[concl] URL には名詞を、メソッドには動詞を置きます。

## リソースとは名前のあるもの {#s-uubcqg}
[0] では、リソースとは何でしょうか。この教材では、画面で扱う「もの」のことです。NAsVI では、まず 3 つあります。
[1] 1 つめは、場所です。企画や駐車場で、運営が登録します。
[2] 2 つめは、スタンプです。混雑や感想で、来場者が押します。
[3] 3 つめは、建物です。AR で認識する建物で、基準画像がついています。
[concl] 画面で扱うものが、そのまま、リソースになります。

## 階層は持ち物の関係 {#s-wim3lq}
[0] リソースの中には、別のリソースの持ち物になっているものがあります。その関係を、パスの入れ子で表します。
[1] 先頭には、API の入り口があります。
[2] その下に、場所、スタンプ、建物のリソースが並びます。
[3] 建物の下には、建物を 1 つ特定する ID がきます。
[4] さらにその下に、その建物の近くの企画を置けます。「この建物の、企画」という持ち物の関係です。
[concl] 入れ子は、持ち物の関係があるときだけ使います。

## 名前のそろえ方 {#s-rpypgn}
[0] 名前の付け方には、決まった正解はありません。大事なのは、全体がそろっていることです。
[1] ここでは、複数形のリソース名、ケバブケースのパス、キャメルケースのキーを推奨案にしています。操作の名前は、要求名と同じにします。OpenAPI の仕様では、この操作の名前は、API 全体で重複してはならず、大文字と小文字も区別されます。
[2] 代替案は、単数形やスネークケースです。どちらでもよいのですが、混ぜてはいけません。
[concl] 規則の中身より、そろっていることが大切です。

## 4 つのメソッド {#s-lfkl3p}
[0] メソッドは、「すること」を表します。主なものは 4 つです。
[1] GET は、読むためのメソッドです。状態を変えません。
[2] POST は、新しく作ったり、押したりします。
[3] PUT と PATCH は、更新です。PUT は全体の置き換えで、PATCH は一部だけの変更です。
[4] DELETE は、指定したものを消します。
[5] なお PATCH だけは、RFC 9110 ではなく、別の仕様の RFC 5789 で定義されています。
[concl] メソッドは、状態を変えるかどうかで選びます。

## 安全と冪等 {#s-blourv}
[0] ここで 2 つの言葉を覚えます。冪等とは、同じ要求を何回送っても、結果が 1 回送ったときと同じになる性質です。
[1] GET は、状態を変えない、つまり安全なメソッドです。何回送っても同じです。
[2] PUT と DELETE は、状態を変えますが、冪等です。同じ要求を 2 回送っても、1 回のときと同じ状態になります。
[3] POST は、安全でも冪等でもありません。2 回送ると、2 件できることがあります。PATCH も、RFC 5789 では、安全でも冪等でもないとされています。
[concl] 再送して困る操作を、先に見つけておきます。

## ステータスコードの帯 {#s-jtfq5c}
[0] ステータスコードは、応答の先頭の 3 桁の数字です。上 1 桁で、大まかな意味が分かります。RFC 9110 では、5 つの帯が定められています。
[1] 2 で始まる数字は、成功です。二百が成功、二百一が作成、二百四が、返す中身がない成功です。
[2] 4 で始まる数字は、呼んだ側の誤りです。四百は不正な要求、四百四は対象がない、四百九は現在の状態と衝突、四百二十二は、形は正しいが処理できない、です。
[3] 5 で始まる数字は、作る側の失敗です。予期しない失敗が、五百です。なお、1 と 3 で始まる帯もありますが、設計で主に使うのは、この 3 つです。
[concl] 数字の帯を見れば、誰が直すべきかが分かります。

## 401 と 403 の違い {#s-45u2iu}
[0] 4 で始まる中で、特に混同しやすい 2 つがあります。認証は「誰か」を確かめること、認可は「してよいか」を確かめることです。
[1] 四百一は、有効な資格情報がない、という意味です。資格情報を付けて送り直せば、通ることがあります。
[2] 四百三は、要求は理解したが、拒否する、という意味です。同じ資格情報を送り直しても、直らない前提です。
[3] たとえば、運営だと確かめられないのが四百一で、出展者が他の出展者の場所を更新しようとするのが四百三です。なお、運営の認証方式は、まだ決まっていません。
[concl] 先に誰かを確かめ、次に、してよいかを確かめます。

## エラーの形をそろえる {#s-la7iqf}
[0] 失敗したときの応答の中身も、そろえておく必要があります。呼んだ側が、次にすることを決められるようにするためです。
[1] 「失敗しました」だけでは、呼んだ側は何もできません。
[2] 独自の形を決める方法があります。たとえば、エラーの中に、コードとメッセージを入れます。コードを見れば、次の動作を決められます。
[3] 標準の形もあります。RFC 9457 では、application/problem+json という形式で、種類、題名、ステータス、詳細などを返します。標準に合わせるか、独自にするかは、ゲート 2 で決めます。
[concl] 標準と独自のどちらにするかは、人が決めます。

## 入力の検査 {#s-p5iqve}
[0] 受け取る側は、入ってきた値が正しいかを、必ず確かめます。確かめる観点は、4 つあります。
[1] 1 つめは、必須かどうかです。たとえば、場所の名前は必須にする、などです。
[2] 2 つめは、形式です。位置は、緯度と経度の組、などです。
[3] 3 つめは、範囲です。文字数の上限などです。
[4] 4 つめは、業務ルールです。たとえば、現在地が場所の上にあるときだけ、スタンプを押せる、などです。概念設計の事前条件が、そのまま、このエラーの候補になります。形が正しくない場合は四百、形は正しいが処理できない場合は四百二十二を使います。
[concl] 概念の事前条件は、そのまま、エラーの候補になります。

## 状態と遷移 {#s-cmfs36}
[0] ものには状態があり、操作が状態を変えます。
[1] まず、場所は、まだ登録されていません。
[2] 登録すると、登録済みになります。
[3] 削除すると、削除済みになります。
[4] 削除済みの場所を更新しようとしても、対象がないので、四百四を返します。
[concl] できない遷移は、エラーにします。

## 一覧は全部返さない {#s-nv6dob}
[0] 一覧を返す API には、特別な注意が要ります。
[1] 全件を返すと、件数が増えたときに、遅く、重くなります。
[2] 区切って返せば、一定の速さを保てます。そのかわり、1 回に返す上限、並び順、絞り込みの項目を、先に決める必要があります。区切り方には、何件目から取るか、前回の続きから取るか、などの方式があります。
[concl] 一覧は、上限と並び順を、先に決めます。

## 再送と同時更新 {#s-rvjpkt}
[0] 通信は、途中で切れることがあります。人は、反応がなければ、もう一度押します。
[1] スタンプを押します。
[2] ところが、応答が届きません。
[3] そこで、もう一度押します。
[4] サーバーが両方を受け取っていたら、同じスタンプが 2 つできます。2 人が同時に同じ場所を更新したときも、似た問題が起きます。このときは、四百九で衝突を知らせます。
[concl] 同じ要求が 2 回来ても、壊れない形にします。

## 連動が途中で失敗したら {#s-5kolcs}
[0] 1 回の要求で、複数の動きが続くことがあります。たとえば、場所を登録すると、検索にも載せます。
[1] 検索への登録が失敗したとき、全体を失敗にするなら、場所の登録も取り消します。呼んだ側は、やり直すだけで済みます。
[2] 一部だけ成功にするなら、場所は残りますが、検索には出ません。呼んだ側から見ると、あるのに探せない、という状態になります。
[concl] 途中の失敗の扱いは、先に決めておきます。

## 返してよい項目 {#s-zdla37}
[0] 応答に入れる項目は、慎重に選びます。
[1] 他の来場者の現在地は、返しません。返すのは、場所とスタンプの位置です。
[2] カメラの映像と画像は、保存も送信もしません。返すのは、認識の結果だけです。
[3] データベースの内部の列を、そのまま返してもいけません。返すのは、画面が使う項目だけです。
[concl] 返す項目は、画面が必要とするものだけにします。

## 上限と速度 {#s-p7wi3e}
[0] 使う人が増えても止まらないように、上限を決めておきます。
[1] 1 つめは、レート制限です。短い時間に送れる回数の上限です。
[2] 2 つめは、タイムアウトです。応答を待つ時間の上限です。
[3] 3 つめは、最大サイズです。1 回に送れる大きさで、建物の基準画像などに関わります。
[concl] 上限は、来場者数の見込みから決めます。なお、その見込みは、まだ決まっていません。

## 公開後は変えにくい {#s-b34ejk}
[0] API は、使う側が増えるほど、変えにくくなります。直すと、誰かが壊れるからです。
[1] 壊れる変更は、項目を消す、名前を変える、任意だった項目を必須にする、などです。
[2] 壊れにくい変更は、任意の項目を足すことです。
[3] 版を付けるかどうかも、決めることの 1 つです。ハッカソンの期間中は付けない、という案があり、仮置きにしています。
[concl] 迷う点は、公開する前に決めます。

## OpenAPI は設計図 {#s-owet7l}
[0] ここまでに決めたことを書く形式が、OpenAPI です。公式の説明では、HTTP の API を、言語に依存しない標準的な形で記述するものです。
[1] 全体は、1 つのファイルです。
[2] 必須の欄は、版を表す openapi と、題名と版を持つ info です。
[3] 操作は paths に、再利用する部品は components に書きます。
[4] paths の中には、パスごとに、get や post などの操作を書きます。操作ごとの応答は、最低 1 つは書く必要があります。なお、x- で始まる欄は、独自の拡張として自由に足せます。
[concl] 設計図があれば、機械が内容を検査できます。

## 設計の順序 {#s-ukqhmt}
[0] 設計は、データベースの構造から始めません。
[1] 最初に、画面と機能で、何をするかを決めます。
[2] 次に、そこから逆算して、API の契約を決めます。
[3] データの形は、最後です。OpenAPI の公式の助言にも、設計を先に書く、という項目があります。
[concl] 画面から逆算して、API を決めます。

## 3 つのゲートと台帳 {#s-yu4erp}
[0] この skill では、人が確かめる場面を、3 つのゲートにしています。
[1] ゲート 1 では、リソースの名前と階層、命名規則を確かめます。
[2] ゲート 2 では、AI が勝手に決めてはいけない事項を、人が決めます。
[3] そのあと、機械が検査します。エラーが 0 になる必要があります。
[4] ゲート 3 では、最終のチェックリストで確かめます。
[5] 決めたことは、台帳に残します。台帳の状態は、要確認、仮置き、確定の 3 つです。
[concl] 決めるのは人です。AI は、仮置きまでです。

## ゲート 2 の 11 区分 {#s-c6onhw}
[0] ゲート 2 で決める事項は、11 の区分に分かれています。
[1] 認証・認可と個人情報は、401 と 403、返してよい項目の話です。バリデーションとエラーは、入力の検査と、エラーの形と、帯です。状態遷移と一覧取得は、状態と遷移、一覧の話です。冪等性・競合と連動は、安全と冪等、再送、連動の失敗です。互換性と非機能は、公開後の変えにくさと、上限と速度です。命名は、名前のそろえ方です。
[concl] 11 区分は、ここまでの知識の総復習です。

## NAsVI に当てはめる {#s-dw4bwg}
[0] 最後に、NAsVI に当てはめます。これは現時点の案で、決まったことと、決まっていないことを分けています。
[1] API の入り口の下に、載せるものと、載せないものがあります。
[2] 載せるのは、共有する状態です。場所、スタンプ、建物です。載せないのは、端末の中で完結するものと、まだ決まっていないものです。
[3] タグは、端末の中に保存すると決まったので、載せません。現在地と行き先は、来場者を識別するかが未決で、運営の種類も、扱いが未決なので、載せません。
[concl] 決まっていないことは、決めずに残します。

## 出典と確かめた範囲 {#s-qzkcka}
[0] 最後に、この資料の出典です。
[1] OpenAPI の仕様の三点二点一版と、公式の入門サイトを読みました。
[2] HTTP の RFC 9110、エラー形式の RFC 9457、PATCH の RFC 5789 を読みました。
[3] この資料のもとになった skill の元の資料には、参考資料の記載がありません。この skill の設計の根拠は、書籍や公式資料ではなく、人が決めたものです。
[4] 仕様の中の parameters と Schema の詳細は、読んでいません。
[concl] 出典は、確かめた範囲だけを書きました。
