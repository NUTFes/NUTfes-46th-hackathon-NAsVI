NAsVI 勉強会資料(api-design の確認ゲート用)

API 設計の基礎

設計が初めてでも、ゲートで判断できるようになる

API とは約束である

使う側と作る側のあいだに、決まりごとを置く。

約束が決まれば、両側は別々に作れる

1 回の通信は要求と応答

呼ぶ側が要求を送り、作る側が応答を返す。

例: GET /places → 200 と、場所の一覧

すべての API は、この往復でできている

「もの」と「すること」を分ける

URL に名詞、メソッドに動詞を置く

リソースとは名前のあるもの

NAsVI の画面で扱う「もの」は、まず 3 つ。

画面で扱うものが、リソースになる

階層は持ち物の関係

入れ子は「この建物の、企画」という持ち物の関係を表す。

入れ子は、持ち物の関係にだけ使う

名前のそろえ方

規則の中身より、そろっていることが大事

4 つのメソッド

PATCH だけは、別の仕様(RFC 5789)で定義されている

メソッドは、状態を変えるかで選ぶ

安全と冪等

冪等(べきとう)とは、同じ要求を何回送っても、結果が 1 回と同じこと。

再送して困る操作を、先に見つける

ステータスコードの帯

応答の先頭の 3 桁の数字で、結果を伝える。

数字の帯で、誰が直すかが分かる

401 と 403 の違い

認証は「誰か」、認可は「してよいか」。

誰かを確かめてから、してよいかを確かめる

エラーの形をそろえる

呼んだ側が、次の動作を決められる形で返す。

標準か独自かは、ゲート 2 で決める

入力の検査

受け取る側は、入力が正しいかを必ず確かめる。

事前条件が、そのままエラーの候補になる

状態と遷移

ものには状態があり、操作が状態を変える。

削除済みの場所を更新すると、404 になる

できない遷移は、エラーにする

一覧は全部返さない

一覧は、上限と並び順を先に決める

再送と同時更新

通信は途中で切れる。人は、もう一度押す。

同じ要求が 2 回来ても壊れない形にする

連動が途中で失敗したら

1 回の要求で、複数の動きが続く。例: 場所を登録すると、検索にも載せる。

途中の失敗の扱いは、先に決めておく

返してよい項目

返す項目は、画面が要るものだけにする

上限と速度

使う人が増えても、止まらないための上限。

上限は、来場者数の見込みから決める

公開後は変えにくい

使う側が増えるほど、直すと誰かが壊れる。

迷う点は、公開前に決める

OpenAPI は設計図

API を、機械が読める形で書く仕様。

設計図があれば、機械が検査できる

設計の順序

データベースの構造から始めない。

画面から逆算して、API を決める

3 つのゲートと台帳

台帳の状態は 3 つ: 要確認、仮置き、確定

決めるのは人。AI は仮置きまで

ゲート 2 の 11 区分

認証・認可、個人情報401 と 403、返してよい項目
バリデーション、エラー入力の検査、エラーの形、帯
状態遷移、一覧取得状態と遷移、一覧は全部返さない
冪等性・競合、連動安全と冪等、再送、連動の失敗
互換性、非機能公開後は変えにくい、上限と速度
命名名前のそろえ方
11 区分は、ここまでの知識の総復習だ

NAsVI に当てはめる

現時点の案。決まったことと、未決のことを分ける。

決まっていないことは、決めずに残す
