# 技術スタックとデプロイの決定記録(暫定)

作成: 2026-11-23 / 状態: **暫定**(チーム確認前)
前提にした概念設計: `concept-design/` の `567b90b`(#33、D-033 まで反映)。API 設計は `concept-design/api/review-ledger.yaml`(API-24・25 を含む)

各決定に、理由と「見直す条件」を付ける。見直す条件が起きたら、決定を差し替える。

## 前提(チームから聞いたこと)
- 言語は TypeScript であればよい。ほかの制約はない。
- フロントは Vue を使ってみたい(開発者の希望)。
- Cloudflare で一括して構築し、管理者ページは Cloudflare Access(ゼロトラスト)で守りたい。
- チーム人数は 5 人。想定来場者は、前回が延べ約 10000 人(2 日間、重複を含む)で、実人数は数千。審査基準は考慮しない(OQ-6、2026-11-23)。
- 来場者は不特定多数。認証が要るのは運営側。

## 端末に任せる方針(P1。API 設計・概念設計は変えない範囲)

| 任せる | 内容 |
|---|---|
| 一覧のキャッシュと差分 | 場所・建物・見取り図を端末に保存する。再び開いたときは、保存した cursor から `/changes?since=` だけつなぐ。全件取得は初回と `resync` のときだけ(API-42 のとおり) |
| 固定データのキャッシュ | 建物の輪郭と見取り図を、版つきで保存する。運営が読み込み直したら、版が変わって取り直す |
| 接続の節約 | 画面が裏に回ったら SSE を閉じ、戻ったら `since` でつなぎ直す |
| 再接続の揺らぎ | 指数的な待ち時間 + 0〜10 秒のランダムな揺らぎ。429 の `Retry-After` に従う |
| 期限の判定 | 端末が `expiresAt` から消す(API-38) |
| 混雑の集計 | 有効なスタンプから、場所ごとの濃淡を端末で計算する |
| 描画の負荷の抑制 | 画面が見えないとき、描画と GPS の頻度を下げる。ラベル数に上限を設ける |

**任せない**: 認可、`proof` の照合、cursor と順序、期限の値と範囲の検査、レート制限、OSM の輪郭の取得(端末から OSM を直接呼ばない)。端末どうしの直接通信(P2P)も採らない。
**外した案**: 検索の端末化。概念設計(`Search`)と API 設計(`search`・`searchNatural`)の変更になるため、今回は扱わない。Laya(OQ-8)の動かす場所とあわせて、必要になったときに決める。

## 調べたこと(2026-11-23。二次情報を含む。数値は公式ページで再確認する)
- Workers の HTTP 応答は、クライアントがつないでいる限り、壁時計の時間に上限がない。待ち受けの時間は CPU 時間に数えない(無料プランの CPU は 1 リクエスト 10 ms、有料は既定 30 秒)。
- Durable Objects は無料プランでも使える(SQLite 版のみ)。WebSocket の Hibernation を使うと、待機中の時間課金を避けられる。SSE の応答を保持する場合は、応答が続く間オブジェクトが起きたままになる。
- 1 つの Durable Object は 1 スレッドで動く。配信の中継を 1 つに集めると、直列になる。
- 未確認: 1 つのオブジェクトに保てる接続数の上限、無料枠(1 日 100,000 リクエストなど)での収まり、SSE と WebSocket のどちらが合うか。
- `mock/index.html`(PR #4・#5)の地図は、ソースを読んだだけで、画面は動かしていない。
