## 注意
レビューで、各画面の PR に次の必須条件を付けている(#147・#149・#154・#155・#157・#160・#166)。S-08 はこれを満たすこと。
- 場所のデータの 3 状態(Place ストアに「読み込み完了」の印は無いので、S-08 が次で判定する)。`state.syncing` だけで判定しない(再試行中に出入りする)。
  - 使える: ストアの places が 1 件以上(キャッシュの先出しも含む)、または `start()` が解決し、`state.failedKeys` に 'places' が無く `state.error` も無い(0 件で成功した場合もここ。空の一覧として出す。ただし S-02 の PlaceCard は 0 件を「読み込み中」とみなすので、S-08 のテストで確かめるのは ListView などの一覧までとする。PlaceCard の 0 件の扱いは、`failedKeys` を使う別の対応として後続で行う: issue #167)。
  - 読み込み中: 上に当たらず、`start()` が未解決。
  - 失敗: キャッシュが無く、`start()` が解決したあとも `state.failedKeys` に 'places' がある、または `state.error` がある(bootstrap が throw した経路は、`start()` が resolve し、`failedKeys` は空で、`state.error` だけが立つ)。失敗の画面と再試行の操作を出す。再試行は、`state.failedKeys` が空でないときは `refresh(failedKeys)`、`failedKeys` が空のとき(throw 経路)は `resync()` を使う(`refresh([])` は何も再取得しない)。snapshot がまだ無い throw(`loadCachedOrFetch` の失敗)では `refresh()` が memo 済みの `start()` を返して再試行にならないので、再読み込みを促す。キャッシュがあって取得が失敗したときは、「使える」として出したうえで、失敗の通知と再試行の操作を足す(オフライン起動でキャッシュがあると、`failedKeys` に 'places' が入るため)。
- S-02・S-03 は「一覧が 0 件なら未取得」とみなす暫定のガードを持つ。S-08 が取得完了まで画面を出さないので、このガードは「全場所が削除された」場合に自動 clear しないだけの備えになる。
- 行き先の解除は、W-09(`placeRemoved`)が先に行い、画面(S-03)の `watch` は一覧の取り直しで消えていた場合の備えである。
- W-09 の再試行の契機は `online` のみで、bootstrap が throw した経路(`failedKeys` が空で `state.error` だけが立つ)は online でも再試行されない。オンラインのまま API が落ちたときの再試行も無い。再試行の操作(ボタン)は S-08 が持つ。取得中に適用した出来事が差し替えでいったん戻る件は、実機で確かめる(issue #167)。
- 410 resync と接続の作り直しは W-09 が行う。画面側で重ねて処理しない。
- `appVersionChanged` のフラグは `web/src/stores/changes.ts` の `versionChanged`。orchestrator には無い。
- 階が null の企画は 1 階とみなす(S-07、チームで確認中)。
- 本番構成(同一オリジンか、Access が 302 を返す構成か)は issue #165 で決定待ち。401 の見せ方は O-01 の admin 側にあり、来場者の画面では扱わない。
- 位置・方位・カメラ画像を外へ送らない。
- チームで決める事項の一覧は issue #167。
- `web/src/views/PlaceCard.test.ts` は S-02 の owns にもある(二重所有)。S-08 が編集してよいのは、App で同期を起動することに伴う mount 方法の修正(PlaceCard を直接 mount する形)に限る。0 件の判定(issue #167)や、テストの検証内容は変えない。PlaceCard.vue の 0 件の扱いは S-02 の所有で、後続の対応とする。
